# Staff self-service and management planning

Implemented on the existing backend; frontend integration is a separate root-owned step.
All routes require a session. POST/PATCH requires its matching `X-CSRF-Token` and same-origin request. `admin` is the management role. Every `staff` account, including legacy `management_scope=manager`, is limited centrally by HTTP method and path. IDs and ownership come from the authenticated user, never a submitted `staff_id` for self-service.

## Staff

- `GET /api/workforce/portal`: `{profile, roster, leave, documents, locations, capabilities, timezone, roster_read_only:true}`. Profile keys: id, first_name, last_name, email, phone, staff_number. Roster includes only the employee's published shifts for the next 90 days. Time zone is Australia/Melbourne. Capabilities: profile, clock, own_hours, own_roster, leave, documents.
- `GET /api/account/profile`: own profile; `PATCH` accepts first_name (required), last_name and phone. Email, role, scope and identity IDs cannot be changed here. Own MFA/password/session-security routes remain available.
- `GET /api/workforce/roster?start=YYYY-MM-DD&end=YYYY-MM-DD`: `{roster, start, end, read_only:true}`. Defaults today through 90 days, maximum span 366 days. Rows have id, staff_id, location_id, shift_date, start_time, end_time, role_label, status, revision, updated_at, published_at, created_by, location_name, location_slug, first_name, last_name. The employee sees only their published rows. Past published rosters can be requested explicitly. Cancelled/draft rows are management-only.
- `GET /api/workforce/leave`: `{requests:[...]}`; latest 200 owned records with id, staff_id, leave_type, start_date, end_date, private_note, status, revision, reviewed_by, review_note, reviewed_at, created_at, updated_at, first_name, last_name, roster_conflicts. Each conflict is `{id, shift_date, start_time, end_time}`.
- `POST /api/workforce/leave`: `{leave_type:'annual'|'personal'|'unpaid'|'other', start_date, end_date, private_note?}` → `{request}`. Notes maximum 1200 characters. Dates inclusive, maximum 366 days, start no earlier than 31 days ago and end no later than two years ahead. Status begins pending. Overlapping pending/approved requests return 409. Existing published shifts are shown as conflicts; management must resolve them before approval.
- `POST /api/workforce/leave/{id}/cancel`: `{revision}` → `{saved:true,id,status:'cancelled',revision}`. Only own pending requests may be withdrawn.
- `GET /api/workforce/documents`: `{documents:[...]}`; latest 200 owned records. Safe fields: id, staff_id, category, title, original_filename, media_type, byte_count, coverage_start, coverage_end, expiry_date, leave_request_id, status, revision, reviewed_by, review_note, reviewed_at, created_at, first_name, last_name, download_url. No filesystem path/storage key/hash is returned.
- `POST /api/workforce/documents`: `{category:'medical'|'professional'|'other', title, original_filename, document_media_type:'application/pdf'|'image/png'|'image/jpeg', document_base64, coverage_start?, coverage_end?, expiry_date?, leave_request_id?}` → `{document}`. Both coverage dates must be present together; coverage end cannot precede start. Linked leave must be the uploader's. Title 2–120 characters; filename 1–180, path components removed and control characters rejected. Decoded size 32 through 5,000,000 bytes. Exact upload path gets a 7,100,000-byte JSON transport limit; normal API requests retain 2,000,000 bytes. File count capped at 200 and aggregate size 200 MB per employee. Status begins pending.
- `GET /api/workforce/documents/{id}/download`: own file only, attachment; private no-store, nosniff, sandbox CSP. Missing or another person's record returns 404. File integrity failures return 409. Storage is outside served public files, encrypted with the existing authenticated data-encryption key and random private filenames. File opens reject symlinks and hold directory/file descriptors. Titles, source filenames and notes are encrypted in the database. Audits contain record IDs/status/dates, never medical narratives or file contents.

## Exact clock and own hours (retained)

- `GET /api/workforce/shift`: `{entry:null|{id,staff_id,location_id,location_name,clock_in,clock_out,break_started_at,entry_version,origin,status,...}, breaks:[{id,entry_id,started_at,ended_at,paid,actor_id}], server_time,today_seconds,week_seconds,long_shift_hours}`. A non-null `entry.break_started_at` means the active shift is on a break.
- `POST /api/workforce/clock`: `{action:'in'|'out'|'break_start'|'break_end',location_slug?,request_id,entry_id?,paid_break:false}`. For clock-in provide location_slug. Subsequent actions provide active entry_id. request_id is a fresh UUID/string of 16–100 letters/digits/underscore/hyphen, retained for retries of the same action. Response `{state:'working'|'on_break'|'clocked_off',entry_id,server_time,...}` may include clock_in, clock_out, break_started_at, break_minutes, hours, worked_seconds, submitted and replayed. Clock-out automatically submits actual elapsed work; no editable hours or roster-to-pay conversion exists.
- `GET /api/workforce/report?period=daily|weekly|fortnightly|monthly|custom&on=YYYY-MM-DD&start=...&end=...`: `{start,end,timezone,generated_at,settings,rows,totals,daily,open_shifts,issues,pay_rules_applied:false}`. Staff queries are self-only; another staff_id is forbidden. Totals use seconds: worked_seconds, approved_seconds, paid_break_seconds, unpaid_break_seconds, unapproved_seconds, exported_seconds, plus shift_count/open_count. Rows include entry_id, version, date, staff_id, staff_name, worker_number, location, clock_in/out, seconds fields, status, origin, approved_by/at, approver, export_batch, notes, review_comment, amendment_of, entry_scope.
- `GET /api/workforce/entries/{id}/history` is own-only. Staff cannot manually add/edit/correct/approve/resubmit/export hours. Existing own historical qualification reads and owned downloads remain available. Legacy qualification uploads are blocked for staff in favour of the encrypted document flow.

## Management (`admin` only)

- `GET /api/management/roster` with the same date filters → `{roster,start,end,staff:[{id,first_name,last_name,staff_number}],locations:[{id,name,slug}]}`. Includes drafts/published/cancelled. Active staff and admin employees are selectable.
- `POST /api/management/roster`: `{staff_id,location_slug,shift_date,start_time:'HH:MM',end_time:'HH:MM',role_label?,status:'draft'|'published'}` → `{shift}`. Defaults Instructor/draft; future dates within two years; end after start on same day.
- `PATCH /api/management/roster/{id}`: full create fields plus required revision → `{shift}` with incremented revision. Staff, location, date/time and status can change before the roster date passes. Cancelled records cannot change.
- `POST /api/management/roster/{id}/publish` or `/cancel`: `{revision}` → `{shift}`. Publish only a draft; cancel preserves the row. Past records preserved. All publish paths reject overlapping published shifts for the same employee, across venues, or approved leave (409). Adjacent shifts allowed. Pending leave is visible to management before approval; approved leave blocks publishing. Transaction locks and revision checks prevent silent overwrites.
- Old `POST/PATCH /api/admin/roster[/{id}]` return 410; no old mutation bypass remains. Use cancellation rather than DELETE. Existing rows retain their IDs and status.
- `GET /api/management/leave` → `{requests}`; `POST /api/management/leave/{id}/decision` `{revision,status:'approved'|'declined'|'cancelled',review_note?}` → `{saved:true,id,status,revision}`. Pending can be decided; approved can be cancelled. No self-review. Approving leave with published shifts returns 409 until shifts are cancelled/reassigned. Leave never modifies clock or payroll entries.
- `GET /api/management/documents` → `{documents}` with management download URLs; `GET /api/management/documents/{id}/download` has the same private attachment protections.
- `POST /api/management/documents/{id}/review` `{revision,status:'accepted'|'rejected',review_note?}` → `{saved:true,id,status,revision}`. Pending only, no self-review, stale revision 409. Acceptance records an administrative review; it does not certify the issuer or declare a file malware-free.

## Explicit limits and remaining operations

File format/signature/completeness/size validation is implemented; malware scanning is not. No document is public or automatically accepted. Existing historical qualification files are retained in their prior storage; new self-service files use encrypted storage. Production still needs private persistent disk/backups including the existing data-encryption key, document retention policy, and a malware-scanning service if required. Staff requests and review results are available in the portal; no external email/SMS is sent. This work does not calculate leave entitlements, leave pay, award rules or payroll from rosters. Those business rules need an owner-approved policy before automation.
